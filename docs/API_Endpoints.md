# API endpoint inventory

Every HTTP endpoint `SentinelAI.Api` exposes, what gates it, and which response format it answers
in. Generated by reading the six controllers in `src/SentinelAI.Api/Controllers`, which are the
only place routes are declared — `Program.cs` calls `MapControllers()` and maps nothing itself.

Base path is `/v1`. Everything is JSON except `POST /v1/scans`, which is `multipart/form-data`.

---

## 1. The whole surface

**Legend.** *Role* is enforced by `[Authorize(Roles = …)]` **and** re-checked in the handler.
*Scope* is enforced in the handler against the token's `scope` claim. *Format* is `envelope` for
`{ isSuccess, message, data }` with camelCase inside, or `read` for a bare snake_case payload with
RFC 7807 `problem+json` on failure — see [`Read_API.md`](Read_API.md) §2 for why there are two.

### Auth — `AuthController`

| Method | Route | Auth | Format |
|---|---|---|---|
| POST | `/v1/auth/register` | none | envelope |
| POST | `/v1/auth/login` | none | envelope |
| POST | `/v1/auth/refresh` | refresh token in body | envelope |
| POST | `/v1/auth/logout` | refresh token in body | envelope |

No `[Authorize]` anywhere on this controller, deliberately: these are the endpoints that hand out
tokens, so requiring one would be circular. `logout` is gated by possessing a valid refresh token
rather than a current access token — the whole point is that it works after the access token has
expired. `refresh` rotates: the presented token is revoked and replaced, so it cannot be reused.

### Account — `AccountController`

| Method | Route | Auth | Format |
|---|---|---|---|
| GET | `/v1/account` | any token | envelope |
| DELETE | `/v1/account` | `admin` | envelope |

Neither takes an id. An account can only read or delete itself — that is the authorization model,
not an omission. The `DELETE` is irreversible: no soft delete, no grace period, because a grace
period means still holding data we said we destroyed (SEC-35).

`GET` returns tenant id and **name**, user id and **email**, role, and the scopes this token
actually holds. The two bolded fields are the reason it exists — a JWT carries neither, so a
console decoding its own bearer token can only show a GUID. Role and scopes come from the token
rather than the row on purpose: a UI gate is answering "will this request be allowed?", and that
is decided by the claims the request will carry.

### Projects — `ProjectController`

| Method | Route | Auth | Format |
|---|---|---|---|
| POST | `/v1/projects` | `admin` | envelope |
| GET | `/v1/projects` | any token | envelope |
| GET | `/v1/projects/{id}` | any token | envelope |

A project *is* a repository, and its id is what the GitHub Action passes as `project-id`.
Re-registering a repository returns **409 carrying the existing id** rather than minting a second
project, so a workflow's `project-id` stays stable across re-runs.

Creation is admin-only because it changes what the tenant *is*; reading is not, because knowing
which repositories your tenant scans is what a viewer needs in order to interpret a report at all.

### Scans — `ScanController`

| Method | Route | Role | Scope | Format |
|---|---|---|---|---|
| POST | `/v1/scans` | — | `scan:write` | envelope |
| GET | `/v1/scans` | — | `scan:read` | read |
| GET | `/v1/scans/{id}` | — | — | envelope |
| GET | `/v1/scans/{id}/summary` | — | `scan:read` | read |
| GET | `/v1/scans/{id}/bundle` | — | `scan:read` | read |
| GET | `/v1/scans/{id}/findings` | — | `scan:read` | read |
| GET | `/v1/scans/{id}/graph` | — | `scan:read` | read |
| GET | `/v1/scans/{id}/chains` | — | `scan:read` | read |
| POST | `/v1/scans/{id}/graph` | — | `scan:write` | envelope |
| POST | `/v1/scans/{id}/audit` | — | `scan:write` | envelope |
| POST | `/v1/scans/{id}/purge` | `admin` | — | envelope |

`POST /v1/scans` is multipart: a `metadata` text part (the runner's `metadata.json`) and a
`bundle` file part (the `.tar.gz`), capped at 64 MB and rejected before the bytes are buffered.
It answers `202` with a poll URL.

The two `POST` stage runners exist because there is no queue-driven worker by default — they are
how the pipeline is driven end to end without a GitHub Action run. `POST …/graph` is fast
(parsing and traversal, no model calls); `POST …/audit` blocks on a live debate and takes
90–140 s, which is why the real path enqueues and polls.

`GET /v1/scans/{id}` is the odd one out on format: it is the poll URL the `202` hands back, its
envelope shape predates the read API, and the Action depends on it.

Filters and paging for `GET /v1/scans` and `GET /v1/scans/{id}/summary` are in
[`Read_API.md`](Read_API.md) §3.1–3.2.

### Reports — `ReportController`

| Method | Route | Scope | Format |
|---|---|---|---|
| GET | `/v1/reports` | `report:read` | read |
| GET | `/v1/reports/{id}` | `report:read` | read |

Addressed by *report* id rather than by scan id, so a report can be linked to directly without the
reader knowing which scan produced it. `404` is a **normal** answer: a report exists only where the
submitter opted into retention, so "not found" can mean the audit ran and, as asked, was not kept.

`report:read` is separate from `scan:read` on purpose. A token allowed to poll a scan's status is
not automatically allowed to read what the debate concluded.

### Debate — `DebateController`

| Method | Route | Auth | Format |
|---|---|---|---|
| POST | `/v1/debates` | **none** | plain JSON |
| POST | `/v1/debates/demo` | **none** | plain JSON |

Synchronous on purpose and only for SEC-02: a live debate is four to seven sequential model calls,
which is far too long for a request thread in production. It exists so the agent stack can be
exercised end to end through the API. Its response is neither the envelope nor the read shape — it
is `DebateResponse`, declared next to the controller.

> **These two carry no `[Authorize]`, and there is no fallback authorization policy** — see
> `AddAuthorization()` in `DependencyInjection.cs:56`, which registers none. They are therefore
> callable by anyone who can reach the host, and each call spends real model tokens. See §4.

### Health — `HealthController`

| Method | Route | Auth | Format |
|---|---|---|---|
| GET | `/v1/health` | none | plain JSON |

Liveness only. Anonymous, and deliberately shallow: it touches no database, no bundle store and no
model provider. A public endpoint that opens a connection per request is a denial-of-service
amplifier, and against a serverless database on auto-pause it would wake the instance on every
probe. Readiness of a dependency is a different question and does not belong on an anonymous route.

## 2. What the console calls today

What `sentinelai-frontend` actually issues, as of this document.

| Console route | Endpoints it calls |
|---|---|
| `/login`, `/register` | `POST /v1/auth/register`, `/login`, `/refresh`, `/logout` |
| `/` | `GET /v1/projects` |
| `/projects` | `GET /v1/projects`, `POST /v1/projects` |
| `/scans/new` | `POST /v1/scans` |
| `/scans/:id/ops` | `GET /v1/scans/{id}`, `POST …/graph`, `POST …/audit`, `POST …/purge` |
| `/scans/:id/findings` | `GET …/findings` |
| `/scans/:id/graph` | `GET …/graph`, `GET …/findings` |
| `/reports/:id` | `GET /v1/reports/{id}`, `GET …/findings` |
| `/debate` | `POST /v1/debates`, `POST /v1/debates/demo` |
| `/account` | `DELETE /v1/account` |

`GET …/bundle` and `GET …/chains` have client methods in `core/api/scan-api.ts` and no caller:
the report embeds its own chains, and no screen shows bundle provenance yet.

### Available and not yet wired

These six are live on the API and nothing in the console calls them yet. Each replaces something
the console currently does without one:

| Endpoint | What it replaces on the console side |
|---|---|
| `GET /v1/scans` | `core/history/recents.ts` — a browser-local index of ids *this browser* opened, keyed by tenant and lost on a cache clear. Its own header calls the missing endpoint "a real gap in the API". |
| `GET /v1/reports` | the same local index, report half |
| `GET /v1/scans/{id}/summary` | the findings page counting the rows it has loaded, because under a cursor it cannot honestly claim the scan's total |
| `GET /v1/projects/{id}` | resolving a scan's `project_id` by downloading every project the tenant owns |
| `GET /v1/account` | `auth.ts` decoding the bearer token in the browser — which yields claims, and so no tenant name and no email |
| `GET /v1/health` | nothing: with no anonymous endpoint to ping, "the API is down" and "your session expired" are indistinguishable to the browser |

The home screen's own comment already anticipates the first two: *"When a list endpoint lands, the
tiles here are where it goes, and the layout already has the shape for it."*

## 3. Rules that hold across the whole surface

**Tenant scoping comes from the token and nowhere else.** No endpoint accepts a tenant id in a
route, a query string or a body. Every `ITenantOwned` entity also carries a global EF query
filter, and the handlers still write the predicate explicitly on top of it — SEC-32's warning is
that isolation which holds only because of a filter configured elsewhere is isolation nobody can
verify at the call site.

**Another tenant's resource is `404`, never `403`.** A 403 confirms the id is real and merely
someone else's, which is itself the leak. The same rule covers the list filters: a `project_id`
belonging to another tenant matches nothing rather than erroring.

**Roles and scopes are different axes.** A scope says what a *token* may do; a role says what its
holder *is*. `admin` and `analyst` get identical scopes on purpose — what separates them is the
role-gated endpoints (project creation, bundle purge, account deletion). The Action's machine
token carries `scan:write` and **no role at all**, which is why those three are role-gated rather
than scope-gated: a token that can submit scans must not be able to register repositories or
delete the account.

**Role → scopes**, per `RoleScopes`:

| Role | Scopes |
|---|---|
| `admin` | `scan:write`, `scan:read`, `report:read` |
| `analyst` | `scan:write`, `scan:read`, `report:read` |
| `viewer` | `scan:read`, `report:read` |
| *(machine token)* | `scan:write` |

**Every role-gated handler re-checks the role** even though the attribute already gates the route,
so the handler stays provably correct read on its own.

## 4. Known gaps

- **`POST /v1/debates` and `/v1/debates/demo` are unauthenticated.** No `[Authorize]` on the
  controller and no fallback policy, so anyone who can reach the host can start a debate, and each
  one spends real model tokens against the configured provider. On the live Azure Container App
  this is an unauthenticated cost and availability exposure, not a theoretical one. The fix is one
  attribute; it is called out here rather than applied because it changes who can reach a shipped
  endpoint.
- **Two response formats in one API.** Deliberate and contained — see [`Read_API.md`](Read_API.md)
  §2. `GET /v1/scans/{id}` in particular answers in the envelope while its siblings under the same
  route answer in the read format, because the Action depends on its shape.
- **No `DELETE /v1/projects/{id}`.** A project cannot be deregistered without deleting the whole
  account. Deleting one would have to cascade its scans, findings, graph, chains and reports, and
  what should happen to a workflow still passing its `project-id` is a product decision, not an
  implementation detail.
- **No tenant-wide totals.** `GET /v1/scans/{id}/summary` counts one scan's contents. Nothing
  answers "how many scans does this tenant have" — do not infer it by walking pages.
- **No role or user management.** `POST /v1/auth/register` always creates a brand-new tenant with
  the caller as its first admin. There is no invite, no second user, and no way to change a role,
  so `analyst` and `viewer` are reachable only by minting a token by hand.
